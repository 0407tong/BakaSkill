# 性能基准

> 机器：Windows 11 Home 22631　Rust 1.98.1（MSVC）　Node 26.10.0
> 数据规模：**1000 个 Skill**（由 `scripts/gen-fixtures.mjs` 生成，长短描述混合、标签数 0–5）
> 记录时间：2026-10-01

---

## 1. 结论汇总

| 基准项 | 目标 | 实测 | 结论 |
| --- | --- | --- | --- |
| **列表首屏**（1000 条） | < 1000 ms | **约 125 ms**（扫描 122ms + 索引读取 3ms） | ✅ 余量约 8 倍 |
| **搜索过滤**（1000 条） | < 100 ms | **0.23 ms**（最慢一项） | ✅ 余量约 400 倍 |
| **单条启停端到端** | < 200 ms | **0.90 ms**（20 轮最坏值） | ✅ 余量约 220 倍 |
| **全文搜索**（1000 条，含正文） | < 100 ms | **最慢 19 ms**（英文子串） | ✅ 余量约 5 倍 |

## 2. 后端（Rust）

复现：

```bash
cd src-tauri
cargo test --release --test perf_scan -- --ignored --nocapture
```

| 步骤 | 耗时 |
| --- | --- |
| 生成 1000 个 Skill（仅基准搭建，非产品路径） | 513 ms |
| **索引全量重建（冷启动，索引为空）** | **224 ms** |
| **索引读取 1000 条** | **6 ms** |
| **扫描 Agent 目录 + 与中央库归并** | **124 ms** |
| 扫描目录数 | 1000 |
| 跳过项 | 0 |

> 基准 fixture 的正文已由二十来个字节加长到约 1.5 KB，以贴近真实
> SKILL.md。索引重建因此由 166 ms 升到 224 ms、读取由 3 ms 升到 6 ms——
> **这是基准变真实了，不是实现变慢了**。全文搜索的耗时刻意与正文长度挂钩，
> 用假正文量出来的数字没有意义。

要点：

- 扫描使用 `rayon` 在 Agent 之间并行；单 Agent 内部为顺序遍历。
- 归并（中央库 × 各 Agent 实例）走内存哈希表，为 O(n)。
- 索引是 SQLite，`list_all` 一次查询取回全部 1000 行仅 6 ms —— 因此列表首屏
  实际瓶颈不在数据库，而在**扫描**（124 ms）与**前端渲染**。

### 2.1 全文搜索

| 查询形态 | 耗时 | 命中 |
| --- | --- | --- |
| 两字中文「基准」（短于 trigram 门槛，退化为扫描） | 3 ms | 200（封顶） |
| 长中文短语「基准检索词」（走 trigram 索引） | 14 ms | 200（封顶） |
| 英文子串「toolkit」 | 19 ms | 200（封顶） |
| 专属标记「marker-0500」 | 5 ms | 1 |
| 命中全库「本段用于撑起正文长度」 | 4 ms | 200（封顶） |

要点：

- 搜索走 `LIKE` 而不是 FTS5 的 `MATCH`，因为 `MATCH` 在 trigram 分词器下
  要求查询至少 3 个字符，而两字中文恰恰最常见（详见 `index/mod.rs` 建表处注释）。
- 两字查询最快（3 ms）而带索引的反而十几毫秒，说明**短查询退化为扫描的代价
  在这个规模上可以忽略**——真正的开销在于 trigram 索引本身的回表。
  若日后库涨到万级，再考虑给短查询加前缀表。

### 2.2 单条启停耗时

复现：

```bash
cargo test single_toggle -- --nocapture
```

`links::tests::single_toggle_round_trip_under_200ms` 做 20 轮「启用 → 禁用」，
**取最坏值而非平均值**——这里关心的是"最坏情况下用户要等多久"。

| 指标 | 值 |
| --- | --- |
| 单条启停最坏耗时 | **896 µs** |
| 目标 | 200 ms |
| 余量 | 约 220 倍 |

启停的耗时几乎全部是文件系统调用（创建/删除重解析点 + 回读校验），
没有可避免的开销。因此前端**不做乐观更新**——真实等待不到 1ms，
"先假装成功再回滚"只会增加出错路径。

## 3. 前端（TypeScript）

复现：

```bash
node --experimental-strip-types scripts/bench-filter.mts
```

`applyFilters` 是纯函数，因此可以脱离界面直接计量。

| 场景 | 耗时（1000 条） |
| --- | --- |
| 无筛选（仅排序） | 0.18 ms |
| 按名称搜索（命中少量） | 0.18 ms |
| 按描述全文搜索（命中较多） | 0.23 ms |
| 搜索 + 来源筛选 + 排序 | 0.03 ms |

**最慢一项 0.23 ms**，相对 100 ms 的目标有约 400 倍余量。因此搜索框可以
每次按键即时过滤，无需防抖——防抖只会引入可感知的延迟。

## 4. 为保证以上数字所做的关键决策

| 决策 | 原因 |
| --- | --- |
| **列表虚拟化**（`@tanstack/react-virtual`） | 只渲染可视区域。1000 个卡片全量挂载会直接卡死渲染主线程 |
| **Monaco 按需加载**（`React.lazy`） | 全量 Monaco 打进主 chunk 约 **4.5 MB**。若随首屏加载，列表首屏基本不可能达标 |
| **网格行固定高度** | 虚拟化需要可预测的行高；动态测量会让滚动时高度跳变 |
| **网格列数由容器宽度算出** | 窗口缩放时自适应，且不依赖固定断点 |
| **筛选是纯函数 + `useMemo`** | 避免每次渲染重算 1000 条；同时让性能可脱离界面测量 |
| **索引为派生物** | 中央库元数据的权威来源是 `SKILL.md`；索引可随时重建，坏了不心疼 |

## 5. 已知的体积与优化空间

打包产物（`pnpm build`）：

| 产物 | 体积 | 计入首屏 |
| --- | --- | --- |
| `index-*.js`（主 chunk） | **513 kB**（gzip 160 kB） | ✅ 是 |
| `index-*.css` | 214 kB（gzip 33 kB） | ✅ 是 |
| `SkillEditor-*.js` | 1.31 MB（gzip 333 kB） | ❌ 按需 |
| `SkillEditor-*.css` | 87 kB | ❌ 按需 |
| `ts.worker-*.js` | 6.9 MB | ❌ 从不加载 |
| `css.worker-*.js` | 1.1 MB | ❌ 从不加载 |
| `html.worker-*.js` | 0.74 MB | ❌ 从不加载 |
| `editor.worker-*.js` | 0.30 MB | ❌ 按需 |
| `json.worker-*.js` | 0.43 MB | ❌ 按需 |

**把 Monaco 改为按需加载后，首屏主 chunk 从 4.5 MB 降到 513 kB（减少约 89%）**。
这是列表首屏能达标的关键改动之一。

**优化方向**（未做，可选）：把 `import * as monaco from "monaco-editor"`
换成 `monaco-editor/editor/editor.api` 加显式引入 markdown 语言支持，
预计可去掉 TS/CSS/HTML worker 共约 8.7 MB。当前未做的原因：桌面应用安装包
对体积不敏感，而按需加载已经解决了首屏性能问题；贸然裁剪 Monaco 入口
容易引入难排查的运行时缺功能问题。
