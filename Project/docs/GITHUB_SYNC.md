# GitHub 同步说明

本文档说明 BakaSkill 如何把中央库备份到**用户自己的** GitHub 仓库，以及
为什么要用「独立同步工作区」而不是直接拿中央库当 git 仓库。
**第 5 节的几条实测陷阱是改动这块代码前必读的。**

> 本功能是**用户自有仓库的备份能力**，与「技能市场」无关。
> 代码与界面文案中不得出现任何市场 / 商店 / 分享平台的暗示。

---

## 1. 核心模型：中央库不是 git 工作区

```
中央库   <lib>/skills/<name>/SKILL.md                    ← 用户数据，git 不直接触碰
工作区   %LOCALAPPDATA%\BakaSkill\sync\<仓库名>-<地址摘要>\  ← git 工作区
         └─ skills/<name>/SKILL.md                       ← 与中央库同构
```

两者**同构**：工作区里的 `skills/` 就是中央库 `skills/` 的一份副本，
中央库里没有的东西不会出现在工作区里（除了仓库自己带的）。

工作区目录**按仓库地址分开**。共用一个目录会出事：用户从仓库 A 换绑到仓库 B
时，A 留下的内容还在工作区里（追踪文件，以及 `reset --hard` 不会清理的
未追踪文件），下一次同步就可能把 A 的内容提交进 B——私有仓库的内容进了
公开仓库。按地址分目录之后，换仓库就是换目录，这条路径根本不存在。
目录名里那段可读的仓库名只是为了让人在资源管理器里认得出来。

### 为什么不能把中央库本身当工作区

最初的设计把中央库目录直接当作 git 工作区，于是它与仓库根目录一一对应。后果：

- 仓库里只要有**任何其他内容**（课程笔记、项目代码），历史就不相关，
  `git push` 必然被拒（非快进）；
- 唯一的"出路" `git pull --allow-unrelated-histories` 会把仓库里的
  **无关文件拉进用户的中央库目录**；
- 于是**凡是仓库里已经有内容的用户都无法使用这个功能**。

用独立工作区之后，`git clone` 会带上仓库的完整历史，在其中加入 `skills/`
后推送是**快进**，与仓库里原本有什么无关。仓库既保留了自己的内容，
又获得了 Skill 库。用户的中央库目录里也不再出现 `.git`。

## 2. 操作语义

| 操作 | 做什么 | 绝不做什么 |
| --- | --- | --- |
| **同步**（「立即同步」） | 取回仓库当前状态 → 把中央库里有、仓库里没有或已改动的 Skill 传上去 | 不删除仓库里已有的任何内容；不提交、不改动仓库里与 `skills/` 无关的文件 |
| **取回缺失的 Skill**（原「仅拉取」） | 取回仓库当前状态 → 把仓库里有、中央库没有的 Skill 复制进中央库 | **不覆盖**中央库已有的同名 Skill（哪怕内容不同） |

### 谁说了算

| 情形 | 点「立即同步」 | 点「取回缺失的 Skill」 |
| --- | --- | --- |
| 两边都有同名 Skill，内容不同 | 本地版本传上去，覆盖仓库里那份 | **本地版本保留**，跳过 |
| 本地有、仓库没有 | 传上去 | 不动它 |
| 仓库有、本地没有 | 不动它（但它已经在仓库里了） | 复制进中央库 |
| 从中央库删掉某个 Skill | **不会**从仓库删掉 | 会把它重新复制回中央库 |
| 仓库里与 `skills/` 无关的文件 | 不动、不提交 | 不动 |

一句话：**本地中央库永远是权威**。两个操作都不会用仓库里的内容覆盖
你本地已有的 Skill；而同步在 `skills/` 之外一个字都不改。

最后两行是两个容易反直觉的地方，都是刻意为之：

- **本地删掉不等于仓库删掉**。同步的承诺是"绝不删除仓库里已有的内容"，
  所以在 GitHub 上那份会留着——万一本地那次删除是误操作，仓库里的备份还在。
  想清掉它请在 GitHub 上手动删。
- **拉取会把本地删掉的 Skill 拿回来**，因为它这时确实是"中央库缺少的"。

### 五条硬性约束，任何改动都不得破坏

1. 同步**只暂存 `skills/`**，且每次提交前先清空暂存区。
   用户的仓库里可能有别的东西，"把整个工作区都算我的"在这个模型里不成立。
2. 同步**绝不暂存删除**（`git add --no-all`）。文件从工作区消失的原因可能
   根本不是用户想删（杀毒隔离、清理工具、手工清空目录），而 git 分不清——
   于是"镜像得和本地一致"会变成"帮用户删掉仓库里的东西"。
3. 同步**强制上传 `skills/`**（`git add -f`）。仓库自己的 `.gitignore` 可能
   恰好匹配到 Skill——笔记仓库里写 `*.md` 太常见了，而 Skill 的清单文件就叫
   `SKILL.md`。用户已经把 `skills/` 交给本应用，那条早先写下的规则不该让
   同步**悄悄**失效（被忽略的文件不出现在 `git status` 里，界面会报"同步成功"
   而什么都没传上去）。
4. 镜像**只增改、不删除**。同第 2 条的道理，但发生在文件复制这一层。
5. 拉取**只补齐、不覆盖**。中央库是用户的数据，拉取不该动它已有的东西，
   导入也走"先写暂存区、成功再改名"，绝不留下半截的条目。
6. **取回与同步必须面对同一批条目。** 同步会把 `<中央库>/skills/` 下的
   每个条目原样传上去（目录、目录里没有 `SKILL.md` 的、名字带点的、
   甚至直接放在 `skills/` 下的普通文件），取回就必须能把这些原样还回来。
   取回里**不允许**出现"这看起来不像个 Skill，跳过"之类的判断——
   一旦出现，就会出现"传得上去、取不回来"。

   > 这条是**用一次真实的数据丢失换来的**：曾经在取回里加了"必须含
   > `SKILL.md`"的判断（理由是"只收索引认识的东西"）。用户把一个含
   > `测试1.md` 的目录同步上去、删掉本地，再点「取回缺失的 Skill」——
   > 什么都没回来，界面还显示"仓库里没有中央库缺少的 Skill"。
   >
   > **判断"什么算 Skill"是索引模块的职责**（它决定界面上列出什么），
   > 不该混进"备份 / 还原"这条路径。后者只该问一件事：
   > *同步会传上去的东西，我能原样还回来吗？*

`.bakaskill/`（派生索引）与 `index.db` 位于中央库根目录，而同步只处理
`skills/`，因此**永远不会进版本库**。各系统产生的杂项文件
（`.DS_Store`、`Thumbs.db`、`desktop.ini`、`*.tmp`）在**复制这一层**就被拦掉，
不需要往用户的仓库里写 `.gitignore`。注意 `*.tmp` 只对**文件**成立——
一个叫 `xxx.tmp` 的目录完全可能是个正经 Skill 名。

### 同步失败后一定会重试

`sync_impl` 在"没有新改动"时**仍然会检查有没有未推送的提交并推送**。
少了这一步就会出现一个死局：上一次"提交成功、推送失败"（断网、令牌过期），
工作区是干净的，于是此后每次同步都因为"没有改动"直接返回——用户再点多少次
都推不上去，而界面一直说"已同步"。

## 3. 分支选择

配置里记录了一个分支名，但它不一定在远端存在（手填地址时它只是默认值
`main`，而仓库的默认分支可能叫 `master`）。选择规则：

| 情况 | 采用 |
| --- | --- |
| 远端有配置里的同名分支 | 用配置的那个 |
| 远端没有该名字 | **沿用工作区当前分支**（即克隆下来的默认分支） |

第二条避免了在用户仓库里凭空造出一个与主分支并行的分支——内容看着对，
位置不对。选好之后会把实际使用的分支名写回配置，界面显示的就是真的。

## 4. 认证与凭据

Token **只**存在于 Windows 凭据管理器（`keyring`，service = `com.bakaskill.app`）：

- 不写 `config.json`；
- 不写日志（日志只记长度）；
- 不从后端读回前端（`git_status` 只回答"有没有"）；
- `redact()` 会把可能混进 git 错误输出里的内联凭据抹掉，有测试守护。

**登录有两种方式，都可用**：

| 方式 | 说明 |
| --- | --- |
| GitHub 账号登录（推荐） | 走系统已装的 Git Credential Manager，浏览器里点一下授权，**不需要创建 Token** |
| Personal Access Token | 兜底方案，适合没装 GCM 的环境 |

### Token 权限最小化

若使用 PAT，请用**细粒度 Token**，只授予目标仓库的：

- `Contents: Read and write`（推送与拉取都需要）

**不要**勾选 `Administration`、`Workflows`、`Secrets` 等与同步无关的权限。
BakaSkill 只会用这个 Token 做两件事：`git ls-remote` 探测仓库、
`git push` / `git fetch` 传输内容，以及 `GET /user/repos` 列出你的仓库。

### 凭据泄漏渠道排查清单

改动本模块后，请确认以下位置都没有 token 明文：

1. `config.json`
2. 应用日志
3. 错误信息（界面上显示的）
4. `<工作区>/.git/config` 里的 remote URL（历史上用过内联 token 的话必须清理）

## 5. 故障排查：实测陷阱

### 5.1 `git clone` 一个**空仓库是成功的**

git 只会打印一句 `warning: You appear to have cloned an empty repository.`，
退出码是 0。因此**不能**用"clone 失败就改为 `git init`"来判断远端是否为空：
clone 也会因为网络、凭据、地址拼错而失败，那时 `init` 会把真正的失败悄悄
吞掉，用户要等到推送时才发现不对。

正确做法是先 `git ls-remote` 问远端"你有没有 ref"，再决定克隆还是从零开始。
这一步顺带也验证了地址可达与凭据可用。

### 5.2 `git ls-remote --exit-code` 对空仓库返回 2

`--exit-code` 的语义是"远端没有任何 ref 时以状态 2 退出"，而**空仓库恰恰
没有任何 ref**。于是"仓库可访问但为空"会被判成"无法访问"——
而"新建一个空仓库来备份 Skill"正是本项目最推荐的用法。
**绝不能加该选项。**

### 5.3 Git for Windows 的系统级 `core.autocrlf=true`

Git for Windows 在**系统级** `gitconfig` 里默认 `core.autocrlf=true`，
检出时把 LF 换成 CRLF、提交时再换回去。对"把中央库原样镜像进仓库"这件事
来说，这个转换只会制造麻烦：同一份 SKILL.md 在两边字节不同，"有没有改动"
得靠规范化去猜。

工作区是 BakaSkill 的**派生目录**，因此创建时显式：

```
git -c core.autocrlf=false clone <url> <ws>   # 首次检出就字节忠实
git config core.autocrlf false                # 并持久化到该仓库配置
```

### 5.4 未出生的 HEAD 不是一个分支名

`git init -b main` 之后、还没有任何提交时，`git rev-parse --abbrev-ref HEAD`
**会失败**（`fatal: ambiguous argument 'HEAD'`，退出码 128），而不是回显
`main`。所以分支回退逻辑必须能承受这一步失败，退回配置里的名字——
否则新建的空仓库第一次同步就会走错分支。

### 5.5 git 默认会把中文路径转义成八进制

`core.quotePath` 默认为 `true`，于是 `git status --porcelain` /
`git diff --cached --name-status` / `git ls-tree` 会把这些路径输出成
C 风格的八进制：

```
"skills/\344\270\255\346\226\207\346\212\200\350\203\275/SKILL.md"
```

对一个中文应用来说这是致命的：这些字符串会直接进到界面的变更列表和
**自动生成的提交信息**里，用户看到的就是一堆乱码。
工作区里显式 `git config core.quotePath false` 即可。

（注意：裸仓库或别的仓库没有这条配置，所以测试里断言远端内容时，
也要给命令带上 `-c core.quotePath=false`。）

### 5.6 `Path::exists()` 会跟随链接，判定"存在"必须用 `symlink_metadata`

一个**悬空的 junction**（中央库迁移之后很常见，见 `LINKING.md` §4.3）
在 `Path::exists()` 眼里是"不存在"。若按它判断"目标里有没有同名 Skill"，
就会走进"改名到那个位置"的分支——而那个名字其实被占着，Windows 会拒绝，
整次拉取随之中断，用户只看到一句"写入 Skill 失败"。

判定目录项是否存在要用 `std::fs::symlink_metadata(path).is_ok()`：
它不跟随重解析点。

### 5.7 被 `.gitignore` 匹配的文件不会出现在 `git status` 里

这条会让"同步成功但什么都没传上去"变成一个**静默**失败：判断
"有没有东西要传"如果看 `git status`，被忽略的文件根本不出现，
于是代码认为无事可做、直接返回成功。

因此同步的顺序是**先暂存、再看暂存区**（`git diff --cached --name-status`），
并且用 `git add -f` 强制纳入 `skills/`。暂存区的回答也天然就是
"这次究竟要提交什么"，与生成的提交信息永远一致。

### 5.8 工作区可以安全地"直接对齐远端"

工作区的内容 = 远端仓库内容 ∪ 中央库镜像，**两者都能完整重建**：
远端内容可以重新 clone，镜像内容可以重新从中央库复制。
因此 `refresh_workspace` 在分叉时可以直接 `reset --hard origin/<branch>`，
既不用合并提交（那正是原设计里用户看不懂的东西），也不会丢数据。

这条推论依赖一个前提：**推送前一定先镜像**。若日后有人改成
"先提交、再镜像"，这个安全性就不再成立，注释里的这行话必须同步改掉。

换句话说，"可重建"保证的是**中央库里有的东西**不会因为对齐而丢失。
反过来说也成立：如果某个 Skill 已经从中央库里删掉、又恰好卡在一次
未推送的提交里，那次对齐就会把它丢掉——而它在用户那边本来也已经删了。

## 6. 首次使用流程

1. 在设置页的「GitHub 同步」里登录（账号登录或 Token）。
2. 点「加载仓库列表」，从你的仓库里选一个（或手动填写地址）。
   - **推荐新建一个空仓库**：Skill 备份与项目代码分开更清晰。
   - 但**已经有内容的仓库同样可用**——同步不会动你原有的文件。
3. 点「同步到仓库」。首次同步会：克隆仓库到工作区
   （空仓库则 `init` + 绑远端）→ 镜像 `skills/` → 提交 → 推送。
4. 另一台机器上重复 1–2 步，点「取回缺失的 Skill」把 Skill 拉到中央库。

## 7. 界面上的操作

| 按钮 | 位置 | 作用 |
| --- | --- | --- |
| 用 GitHub 账号登录 / 保存 Token | 登录区 | 见 §4 |
| 加载仓库列表 / 手动填写地址 | 仓库区 | 绑定要同步的仓库 |
| 同步到仓库（已同步过时显示「立即同步」） | 同步区 | §2 的「同步」 |
| 取回缺失的 Skill | 同步区 | §2 的「取回」 |
| 移到一旁（不删除） | 中央库残留 `.git` 提示 | 旧版本在中央库里留过 `.git`，这里把它**重命名**到 `.git.bakaskill-old-<时间戳>`，不删除任何东西 |

> 那张提示卡判断的是**磁盘上此刻有没有** `<中央库>/.git`，因此它不缓存答案。
> 如果你是在应用之外（资源管理器里）把 `.git` 删掉的，切走再切回设置页即可，
> 卡片会随之消失。真要在文件管理器里彻底删除也可以——先确认一下
> 那个仓库里没有别处没有的内容（`git ls-tree -r --name-only HEAD`）。

状态卡三个数字的含义：

- **待同步改动**：工作区里 `skills/` 下尚未提交的改动条数
- **未推送**：本地领先远端的提交数
- **仓库新增**：远端领先本地的提交数（在"借用已有仓库"的模型里这是常态，
  大多来自另一台机器；点任一按钮都会先取回它们）

变更列表里以 `−` 标出的是**本地已删除**的 Skill，它们不会被同步到仓库
（见 §2 的「谁说了算」），界面上会就此单独说明一句。
